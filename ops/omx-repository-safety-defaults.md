# 옴엑스 저장소별 안전 기본값

작성일: 2026-04-15

## 목적
옴엑스를 어디서 어떻게 허용할지 기본값을 고정해서, 요청이 들어왔을 때마다 판단이 흔들리지 않게 한다.

## 공통 최상위 원칙
- 기본값은 옴엑스 비사용이다.
- 민이 명시적으로 요청한 경우에만 옴엑스를 켠다.
- 옴엑스가 끝났다고 바로 성공으로 보지 않고, 루나가 다시 검증한다.
- 기존 더티 상태와 이번 변경을 분리하지 못하면 완료로 보고하지 않는다.
- 위험한 명령, 넓은 범위 수정, 샌드박스 우회는 자동 기본값으로 쓰지 않는다.
- 민이 옴엑스를 요청한 뒤에는 모드 선택과 omx 내부 절차를 사용자에게 다시 묻지 않는다.
- 필요한 명확화는 `딥 인터뷰`, 계획 고정은 `랄플랜`, 실행은 `랄프` 또는 `팀` 으로 루나가 직접 정한다.
- omx 표준은 반드시 tmux 안에서 Codex를 실행하는 것이다.
- 즉 루나는 omx 작업을 tmux 세션 없이 바로 시작하지 않는다.

## 저장소별 기본값

### 1. 티커 아트로포스
- 기본 모드: 일반 코덱스
- 옴엑스 허용 조건
  - 민이 옴엑스를 명시적으로 요청함
  - 작업 범위가 분명함
  - 검증 명령을 미리 적을 수 있음
- 권장 사용 예
  - 작은 문서 또는 좁은 코드 수정은 `옴엑스 실행`
  - 끝까지 미는 중간 규모 작업은 `옴엑스 랄프`
  - 병렬 이점이 분명한 경우만 `옴엑스 팀`
- 금지 기본값
  - 요청 없는 상시 사용
  - 저장소 전체를 한 번에 뒤집는 넓은 수정
  - 검증 없는 완료 보고
- 필수 검증
  - `git status --short`
  - 변경 파일 확인
  - 관련 시험 실행
  - 로그 경로 기록

### 2. 페이퍼클립 사용자 화면 또는 제품 저장소
- 기본 모드: 일반 코덱스
- 옴엑스 허용 조건
  - 민이 명시적으로 요청함
  - 화면 또는 기능 범위가 좁음
  - 브라우저 검증 또는 빌드 검증 경로가 있음
- 보수 규칙
  - 넓은 라우팅 개편, 데이터 경계 변경, 배포 스크립트 수정은 기본 금지
  - 더티 워킹트리가 심하면 먼저 분리 전략부터 세운다
- 필수 검증
  - 변경 파일 기준 차이 확인
  - 관련 시험 또는 빌드
  - 필요 시 브라우저 확인

### 3. 옵시디언, 콘텐츠, 문서 중심 저장소
- 기본 모드: 옴엑스 불필요
- 해석
  - 문서 정리와 초안 작성은 루나 기본 흐름으로 충분하다
  - 옴엑스를 쓸 이유가 명확하지 않으면 쓰지 않는다
- 예외
  - 민이 특정 실험으로 옴엑스를 직접 요청한 경우만 허용

### 4. 배포, 자동화, 비밀값, 운영 스크립트 중심 저장소
- 기본 모드: 옴엑스 금지에 가깝게 운영
- 이유
  - 승인 흐름과 검증 실패 비용이 크다
  - 잘못된 자동 수정의 반경이 넓다
- 예외 허용 조건
  - 민이 명시적으로 요청함
  - 변경 범위가 한정됨
  - 사전 백업 또는 되돌리기 경로가 있음
  - 후속 검증 명령이 명확함

## 모드 선택 기본값
- 범위와 비목표 정리 필요: `옴엑스 딥 인터뷰`
- 구현 순서와 검증 경로 고정 필요: `옴엑스 랄플랜`
- 작은 작업: `옴엑스 실행`
- 끝까지 미는 작업: `옴엑스 랄프`
- 병렬 작업: `옴엑스 팀`

단, 위 선택은 어디까지나 민의 명시 요청이 먼저 있어야 한다.

## 착수 전 확인
1. 민이 옴엑스를 직접 요청했는가
2. 저장소와 작업 범위가 분명한가
3. 기존 더티 상태를 캡처했는가
4. 검증 명령을 미리 적었는가
5. 로그와 산출물 경로를 남길 수 있는가

## 현재 기본 결론
- 옴엑스는 상시 엔진이 아니다.
- 민의 명시 요청이 있을 때만 켜는 예외 경로다.
- 안전 기본값은 항상 일반 코덱스와 수동 검증 쪽에 둔다.
