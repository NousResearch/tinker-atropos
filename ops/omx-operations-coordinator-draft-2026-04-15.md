# 옴엑스 운영 코디네이터 초안

작성일: 2026-04-15

## 목적
민이 명시적으로 요청할 때만 사용하는 옴엑스 흐름을 운영 기준, 검증 기준, 저장소별 안전 기본값 중심으로 관리한다.

## 한줄 역할
옴엑스를 상시 구현 엔진으로 두지 않고, 언제 어떻게 쓰는지가 흔들리지 않도록 관리하는 운영 코디네이터.

## 왜 필요한가
- 옴엑스는 기본 코딩 흐름이 아니라 요청 기반 예외 경로다.
- 코덱스 일반 실행과 달리 승인, 모드 선택, 더티 상태 구분, 결과 검증 규칙이 더 중요하다.
- 민의 원칙상 증거 없는 완료 보고는 금지다.
- 따라서 실제 구현보다 운영 규칙과 회고가 누적되어야 가치가 커진다.

## 핵심 책임
1. 사용 기준 관리
- 언제 옴엑스를 쓰는지
- 언제 일반 코덱스로 충분한지
- 언제 팀 모드가 필요한지

2. 모드 선택 관리
- 경계와 비목표가 흐리면 `옴엑스 딥 인터뷰`
- 구현 전에 계획과 검증 순서를 고정해야 하면 `옴엑스 랄플랜`
- 작은 작업: `옴엑스 실행`
- 끝까지 미는 작업: `옴엑스 랄프`
- 병렬 작업: `옴엑스 팀`

2-1. 자율 실행 원칙
- 민이 옴엑스를 명시적으로 요청하면 루나는 모드 선택을 다시 사용자에게 묻지 않는다.
- 필요한 명확화와 계획 수립은 omx 내부에서 `deep-interview`, `ralplan` 으로 직접 처리한다.
- 사용자에게는 중간 확인 대신 검증된 결과와 증거를 보고한다.
- omx 표준은 반드시 tmux 안에서 Codex를 실행하는 것이다.
- 루나는 omx 작업을 바깥 셸에서 바로 치지 않고 tmux 세션을 먼저 띄운다.

3. 검증 기준 관리
- `git status --short`
- 이번 변경과 기존 더티 상태 분리
- 시험 실행 여부
- 로그와 산출물 경로 기록

4. 저장소별 안전 기본값 관리
- 어떤 저장소에서 옴엑스를 허용할지
- 어떤 저장소는 문서 작업만 허용할지
- 위험한 저장소에서 샌드박스 우회 금지 여부

5. 학습 메모 축적
- 어떤 작업에서 성공했는지
- 어떤 프롬프트 구조가 먹혔는지
- 어떤 승인 흐름이 병목인지
- 어떤 저장소에서 오류가 반복되는지

## 권장 산출물
- 저장소별 옴엑스 허용 정책 문서
- 옴엑스 실행 로그 요약 노트
- 성공 패턴 모음
- 실패 패턴 모음
- 복붙용 표준 프롬프트 템플릿

## 운영 원칙
- 민이 명시적으로 요청할 때만 옴엑스를 쓴다.
- 옴엑스 결과는 반드시 루나가 다시 검증한다.
- 기존 더티 상태와 새 변경을 분리하지 못하면 성공으로 보고하지 않는다.
- 상시 실행 에이전트로 두지 않고 요청 기반 코디네이터로 둔다.

## 바로 다음 추천 실행
1. 실제 옴엑스 요청이 들어오면 성공 실패 기록 틀에 한 건 남긴다.
2. 저장소별 기본값 문서에 실제 사례를 덧붙인다.
3. 검증 체크리스트를 실전 로그와 함께 보강한다.
